## 1. Массовый приказ и навигация

Код: [UnitOrders.cpp](../src/core/UnitOrders.cpp), [Formation.cpp](../src/core/Formation.cpp), [Navigation.cpp](../src/core/Navigation.cpp), [UnitMovement.cpp](../src/core/UnitMovement.cpp).

Уже реализованы общий расчёт связности внутри приказа, маршрутное поле на тип движения и прямой маршрут по открытой местности. Заменять их предложением «добавить flow field» было бы повторением существующей работы.

Оставшиеся кандидаты:

- В `Simulation::order` радиус группы вычисляется полным обходом назначений для каждого юнита. Его можно вычислить один раз. Повторные `unit()`/`mutableUnit()` тоже линейные; локальный список участников избавит часть приказа от повторного поиска по ID.
- `Regions` живёт только внутри `planFormation`: следующий приказ заново размечает связность. Кэш по версии статической проходимости и типу движения может помочь при частых приказах на неизменной карте. Нужна инвалидация при зданиях, окружении, рампах и изменении поверхности.
- `searchPath` каждый раз создаёт `blocked`, `cost`, `parent` размером со всю карту, даже при лимите раскрытия 192/256 узлов. Рабочий контекст поиска с переиспользуемой памятью и метками поколений уменьшит выделения и заполнение массивов. Контексты должны оставаться независимыми для вложенных или будущих параллельных поисков.
- При заторе `moveUnit` повторяет поиск через каждые 30 заблокированных тиков. `relaxedFormationPath` может пробовать множество целей, каждая с отдельным A*. Общего бюджета, аналогичного боевому, для этой ветки нет. Сначала посчитать поиски и раскрытые узлы на тик, затем при необходимости ввести детерминированную очередь с гарантией обслуживания всех ожидающих юнитов.
- В `searchPath::clear` каждое проверяемое ребро перебирает все переданные круги препятствий. Пространственный индекс может выбирать тела около отрезка, сохраняя точную проверку пересечения.

Сначала разделить замер приказа на формацию, подготовку участников, маршрутные поля и индивидуальные пути. Лишь после этого менять алгоритм назначения: более быстрый жадный подбор способен ухудшить пересечения траекторий и распределение ролей.

Проверка: [FormationTests.cpp](../tests/FormationTests.cpp), [NavigationTests.cpp](../tests/NavigationTests.cpp), [MovementTests.cpp](../tests/MovementTests.cpp), [EconomyTests.cpp](../tests/EconomyTests.cpp). Сохранить непрерывные позиции, компактную круглую группу, приоритет передних рядов, независимость от порядка выделения и отсутствие прохода через замкнутое окружение. Для добычи сохранить исходное месторождение через повторные попытки и доставки.

## 2. Рендер: отсекать раньше

Код: [SceneRenderer.cpp](../src/render/SceneRenderer.cpp), [TerrainRenderer.cpp](../src/render/TerrainRenderer.cpp).

`Renderer::draw` проходит все строки карты, а `terrainRow` — всю ширину, в том числе при приближении камеры к небольшому участку. Проверка экрана находится внутри обработки клетки. Объекты попадают в общий `items` по известности/видимости тумана, затем сортируются; часть экранных проверок выполняется уже при рисовании.

Что улучшить:

- Получать консервативный диапазон клеток из `WorldView` и прямоугольника мира, с запасом на высоты и грани. Сохранить обработку соседней строки для `drawEarly`.
- До сортировки отбирать объекты по экранным границам спрайта; для большого статического окружения использовать индекс по участкам карты.
- Сохранять ёмкость списков рендера между кадрами. Кэшировать порядок статических объектов только при наличии корректной версии данных, затем объединять с динамическими объектами.

Нельзя отсекать лишь по клетке-якорю: высокое дерево или наклонный спрайт могут попадать в экран из-за его границы. Нельзя объединить весь рельеф в один фон без сохранения перекрытия юнитов передними обрывами.

Измерить отдельно обход клеток, подготовку/сортировку сцены и отрисовку при одинаковом окне и масштабе на картах 128×128 и 512×512. Снимать время обычного оконного рендера: [RenderSnapshot.cpp](../src/render/RenderSnapshot.cpp) использует программный WIC render target и не представляет стоимость игрового кадра на GPU.

## 3. Forge: копии сценария и стоимость кисти

Код: [WorldEditor.cpp](../src/core/WorldEditor.cpp), [TerrainPaint.cpp](../src/render/TerrainPaint.cpp).

`beginStroke` сохраняет полный сценарий для undo. Дополнительно каждый `applyOne` делает `auto s=scenario_`, вызывает `rebuild(s)`, а для некосметических инструментов ещё создаёт проверочную `Simulation`. Один ввод мыши может вызвать несколько `applyOne`. Поэтому большой документ оплачивает полную копию и пересборку несколько раз за событие; история хранит до 32 полных снимков.

В `TerrainPaint::update` каждый вызов сравнивает весь уже применённый список отпечатков. При undo или нарушении общего префикса кэш сбрасывается и покраска воспроизводится заново.

Предлагаемая последовательность:

1. Для Paint/ErasePaint/Base/Decoration не перестраивать occupancy и vision: эти данные по правилам проекта не влияют на проходимость и обзор. Сохранить валидацию материалов и размещения.
2. Объединить подготовку изменений для серии отпечатков одного ввода. Проверку статических изменений выполнять транзакционно, без публикации некорректного состояния.
3. При подтверждённом расходе памяти перейти к истории изменений клеток/объектов/диапазонов paint вместо полных снимков. Undo по-прежнему ровно один на stroke, с восстановлением ID и трансформаций.
4. Дать покраске явную ревизию и диапазон изменений; при отмене пересобирать затронутые chunks, сохраняя порядок наложения отпечатков. Возможны периодические контрольные снимки chunks.

Проверка: [EditorTests.cpp](../tests/EditorTests.cpp), [DataTests.cpp](../tests/DataTests.cpp). Измерять задержку apply/undo/redo и пик памяти на длинном stroke, тысячах paint stamps и насыщенном объектами документе. Сохранить отдельную копию Scenario для play test и документ/undo после F9/F10.

## 4. Прозрачность окружения над юнитами

Код: [UnitOcclusionRenderer.cpp](../src/render/UnitOcclusionRenderer.cpp), вызовы в [SceneRenderer.cpp](../src/render/SceneRenderer.cpp).

`beginUnitOcclusion` для каждого объекта перебирает всех юнитов. Если есть пересечения, выделяет массив пикселей, вычисляет opacity на CPU, создаёт новый Direct2D bitmap и bitmap brush. Слой уже переиспользуется, bitmap и brush — нет. В плотном лесу эта работа может многократно повторяться за кадр.

Предложения: один раз за кадр подготовить экранные окна подходящих юнитов; выбирать пересечения через экранную сетку; переиспользовать буферы и графические ресурсы с контролируемой ёмкостью. Перенос растеризации маски в GPU рассматривать после измерения, а не как обязательную смену всего рендера.

Измерять число вызовов, созданных bitmap/brush, обработанных пикселей и время на лесной сцене с 50–100 юнитами. Сохранить фильтр глубины конкретного объекта и объединение прозрачности без накопления; одна общая маска для всех деревьев может изменить картинку.

## 5. Бой и локальное избегание столкновений

Код: [Combat.cpp](../src/core/Combat.cpp), [CombatTargeting.cpp](../src/core/CombatTargeting.cpp), [CombatMovement.cpp](../src/core/CombatMovement.cpp), [UnitMovement.cpp](../src/core/UnitMovement.cpp).

Уже есть бюджет боевого поиска, лимиты раскрытия и разнесённые интервалы преследования. В движении список ближайших соседей фильтруется до перебора скоростей. Эти ограничения следует сохранить.

Дополнительные точки:

- В `tickCombat::acquire` на кандидата вне дистанции атаки выполняется ещё один обход союзников для штрафа за число атакующих. При массовом выборе целей получается до кубической зависимости от общего числа юнитов. Счётчик ближних атакующих по `(owner, targetId)` уберёт внутренний обход. Его нужно обновлять при изменении целей внутри тика, чтобы не поменять последовательную семантику выбора.
- `targetVisible` для непользовательского владельца каждый раз перебирает его живых союзников и проверяет луч. Возможен кэш результата по владельцу и клетке цели на время неизменного снимка наблюдателей. Не заменять это личным обзором атакующего: текущая проверка объединяет обзор союзников.
- Поиск соседей, `unitObstacles` и финальный `dynamicStep` проходят весь список. Пространственная сетка особенно полезна распределённым армиям; в плотной толпе локальных соседей всё равно много, и выигрыш надо измерять.

Индекс для движения обязан учитывать swept bounds между началом тика и актуальной позицией, обновляться при последовательном движении юнитов и разделять воздушную/наземную занятость. Финальные точные collision-проверки убирать нельзя. Предел supply 100 не следует использовать как доказательство, что в матче всегда не больше 100 тел: есть противники и разные стоимости supply.

Проверка: [CombatTests.cpp](../tests/CombatTests.cpp), [MovementTests.cpp](../tests/MovementTests.cpp), [ProjectileTests.cpp](../tests/ProjectileTests.cpp). Кроме p95/max сохранять нанесённый урон, число вступивших в бой и отсутствие проникновения через кольцо юнитов.

## 6. Туман и миникарта

Код: [FogOfWar.cpp](../src/core/FogOfWar.cpp), [Simulation.cpp](../src/core/Simulation.cpp), [FogMask.cpp](../src/render/FogMask.cpp), [MinimapRaster.cpp](../src/render/MinimapRaster.cpp), [TerrainRenderer.cpp](../src/render/TerrainRenderer.cpp).

Логический туман уже обновляется раз в пять тиков и при смене фазы, а также при соответствующих изменениях окружения. Лучи для уже раскрытых другими наблюдателями клеток пропускаются. Замер показывает, что распределённые наблюдатели обходятся существенно дороже сгруппированных; это не доказывает проблему на каждой карте.

В графической части `FogMask::update` каждый кадр читает все клетки для сравнения. При любом отличии заново интерполирует и размывает полную маску, после чего она целиком передаётся в bitmap. `MinimapRaster::update` также каждый раз обходит рельеф для проверки изменений, хотя растеризация и загрузка миникарты уже кэшируются.

На карте 512×512 маска при 4 пикселях на клетку и padding=1 имеет размер 2056×2056. Массивы `raw`, `horizontal`, `light_`, `pixels_` вместе содержат около 64,5 МиБ данных, без остальных структур и GPU-копии. Это расчёт по размерам буферов, не измерение памяти процесса.

Что делать поэтапно:

1. Ввести надёжные ревизии логической видимости и рельефа, затем исключить проверки неизменных данных каждый кадр. Прямое редактирование `Map::at` сейчас возможно: одна ревизия без изменения всех путей записи сделает кэш некорректным. Учесть замену карты того же размера.
2. Переиспользовать `raw`/`horizontal`; пересчитывать и загружать только изменившиеся области с полями, достаточными для интерполяции и размытия.
3. Для логического обзора попробовать кэш следа неподвижного наблюдателя по клетке, радиусу, воздушному типу и версии препятствий/высот. Удаление наблюдателя должно уменьшать union корректно: нужны счётчики покрытия или эквивалентный механизм.

Логическую видимость нельзя подменять сглаженной маской. Первый блокирующий объект остаётся видимым, воздушный обзор игнорирует препятствия. Изменение known-данных ресурсов и окружения необходимо обрабатывать даже при неизменной геометрии обзора. Динамические маркеры миникарты остаются за пределами кэшируемого растра.

Проверка: [VisionTests.cpp](../tests/VisionTests.cpp), [LightingTests.cpp](../tests/LightingTests.cpp). Дополнить нагрузками на неподвижных/движущихся наблюдателей, смену дня, разрушение/восстановление дерева и замену карты.

## Как внедрять и проверять

Начать с таймеров этапов приказа, тика, подготовки кадра и редакторского stroke. Добавить счётчики поисков/раскрытий A*, проверок соседей, клеток рендера, создания графических ресурсов и объёма обновления масок. Не писать лог внутри каждого горячего цикла: агрегировать и выводить после нагрузки.

Для сравнения фиксировать ревизию, CPU/GPU, разрешение, масштаб камеры, карту, состав армии, конфигурацию сборки и фоновую нагрузку. Сравнивать несколько запусков; указывать p50/p95/max и показатели поведения. Добавить сценарии непроходимой цели, синхронного затора, распределённых армий, большого леса, ночного освещения и длинной истории Forge. Текущий бой использует специально высокий запас здоровья и не заменяет проверку разнообразного матча.

После каждой реализации запускать:

```powershell
./scripts/build.ps1 -Configuration Debug -Test
./scripts/build.ps1 -Configuration Release -Benchmark
```

Регрессии добавлять в соответствующие `tests/*Tests.cpp`; производительность оставлять opt-in, без временных порогов в CTest. Для этого документа Debug-тесты не запускались: исполняемый код не менялся.

Первыми небольшими изменениями разумно сделать однократный расчёт радиуса группы, переиспользование рабочих массивов поиска и исключение пересборки occupancy/vision для косметической кисти. Затем — раннее отсечение рендера и переиспользование ресурсов occlusion. Пространственные индексы и инкрементальный туман внедрять по результатам профиля: они сложнее и затрагивают больше инвариантов. Переписывание на ECS, многопоточность всей симуляции или смена графического API текущими измерениями не обоснованы.

## Используем ли мы ядра, GPU и вычислительные возможности CPU

**Собственные игровые вычисления сейчас преимущественно однопоточные. Утверждать, что ресурсы многоядерного CPU используются оптимально, оснований нет.** Но и загрузка всех ядер сама по себе не является целью: важны время кадра, отзывчивость и энергопотребление.

| Механизм                 | Что установлено по проекту                                                                                                              | Практическое следствие                                                                  |
|--------------------------|-----------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------|
| Потоки игры              | В [GameApplication::run](../src/game/GameApplication.cpp) обработка сообщений, `game_.tick()` и `renderer_.draw()` идут последовательно | Долгий приказ или CPU-расчёт задерживает обработку ввода и следующий кадр               |
| Параллельные задачи      | В `src`/`include` не найдены собственные worker threads, task pool, `std::async`, parallel execution policies или OpenMP                | Дополнительные ядра автоматически не ускоряют навигацию, формации или бой               |
| Forge                    | В [ForgeApplication.cpp](../src/forge/ForgeApplication.cpp) ввод, редактирование и draw также в одном цикле                             | Тяжёлый stroke может задерживать интерфейс                                              |
| Direct2D                 | [Renderer.cpp](../src/render/Renderer.cpp) создаёт single-threaded factory и HWND target с параметрами по умолчанию                     | Это не означает «рендер только на CPU»; фактический аппаратный backend требует проверки |
| Release                  | В сгенерированном CMake cache подтверждены `/O2 /Ob2 /DNDEBUG`, в vcxproj — `MaxSpeed`                                                  | Оптимизация скорости включена; Debug для выводов о быстродействии непригоден            |
| SIMD                     | Ручных SIMD intrinsics и явного `/arch:AVX2` не найдено                                                                                 | Это не доказывает отсутствие SIMD: компилятор может векторизовать циклы сам             |
| Межмодульная оптимизация | Проект явно не включает IPO/LTO или PGO                                                                                                 | Это возможные отдельные эксперименты после устранения повторной работы                  |

`MultiThreaded` в настройке MSVC runtime относится к варианту CRT, а `--parallel` в скрипте — к сборке. Ни то ни другое не распараллеливает игровой цикл. Служебные потоки Windows и драйвера могут существовать независимо от игровых задач. Direct2D с default target допускает разные варианты исполнения; подтверждать аппаратное ускорение только по наличию видеокарты нельзя. См. [Microsoft: ресурсы Direct2D](https://learn.microsoft.com/en-us/windows/win32/direct2d/resources-and-resource-domains).

### Где CPU делает графическую работу

В [NightLightingRaster::update](../src/render/NightLighting.cpp) при активной ночи и наличии источников света выполняются обход всей карты, растеризация видимых поверхностей и перебор источников для пикселей растра. [prepareNightLighting](../src/render/LightingRenderer.cpp) вызывает это на каждом ночном кадре, затем обновляет две bitmap через `CopyFromMemory`. Сам растр уменьшен относительно экрана, но всё равно зависит от разрешения и числа источников.

Отдельная возможность — разделить карту видимых поверхностей и меняющееся освещение: первую кэшировать по камере/рельефу/туману, источники выбирать по экранным участкам, не пересчитывать одинаковое состояние повторно между тиками. `lightSurface` также создаёт геометрию Direct2D на вызов — её стоимость стоит включить в профиль. GPU-обработка освещения перспективна, если CPU-растр действительно занимает существенную долю кадра; это потребует отдельного дизайна backend и визуальных регрессий.

### Что имеет смысл распараллеливать

Первые кандидаты — достаточно крупные независимые задачи над неизменными данными: декодирование изображений, CPU-подготовка масок по строкам/участкам, независимые поиски пути по снимку карты. Использовать постоянный ограниченный пул задач, а не создавать поток на каждый поиск или тик. Direct2D-ресурсы текущего рендера создавать и обновлять на владеющем потоке; передавать туда подготовленные CPU-буферы.

Движение сейчас намеренно последовательно: очередной юнит учитывает уже обновлённые позиции соседей. Простая замена цикла на parallel-for изменит collision-семантику. Параллельное движение потребует отдельных фаз «снимок → предложения → разрешение конфликтов → фиксация», детерминированного порядка и новых регрессий. Аналогично нельзя параллельно записывать общий fog union без отдельного механизма объединения.

Асинхронному результату пути нужны ID запроса, версия карты и проверка актуальности приказа. При отмене приказа старый результат отбрасывается. Для воспроизводимости нельзя позволять случайному порядку завершения задач определять игровые решения. Сначала проверить задачи в пределах тика с барьером и фиксированным порядком применения; более сложную асинхронную модель вводить только при необходимости.

Для SIMD лучше подходят плотные пиксельные массивы тумана/освещения. A* с очередью, ветвлениями и нерегулярными обращениями обычно требует сначала алгоритмических улучшений. Проверять отчёт MSVC `/Qvec-report:2`, а не делать выводы по виду C++-цикла; компилятор различает автовекторизацию и автопараллелизацию. См. [Microsoft: Auto-Parallelization and Auto-Vectorization](https://learn.microsoft.com/en-us/cpp/parallel/auto-parallelization-and-auto-vectorization?view=msvc-170).

Повторяющиеся углы перебора скоростей в `moveUnit` можно представить заранее рассчитанной таблицей; сначала проверить, не устранил ли повторные вычисления оптимизатор. Не включать глобально `/fp:fast` ради чисел в бенчмарке: геометрические границы столкновений и воспроизводимость требуют проверки. AVX2, если даст пользу, добавлять с проверкой возможностей CPU и базовым вариантом исполнения либо сознательно менять системные требования.

## Как оценивать производительность самой игры

Нужны три отдельных уровня измерений: текущие headless-бенчмарки для алгоритмов; профиль функций/потоков для поиска причин; длительный прогон оконной игры для пользовательского результата. Удобный FPS-счётчик без frametime, пиков и задержек приказов недостаточен.

### Метрики и точки измерения

| Метрика                                                 | Где/как измерять                                                            | Что показывает                                                 |
|---------------------------------------------------------|-----------------------------------------------------------------------------|----------------------------------------------------------------|
| Время кадра p50/p95/p99/max                             | Последовательные кадры и события представления окна                         | Равномерность движения и пропуски кадров                       |
| Тик p50/p95/p99/max                                     | Вокруг `Simulation::tick`, дополнительно по подсистемам                     | Стоимость симуляции и её скачки                                |
| Накопленный долг симуляции                              | Accumulator и число догоняющих тиков на кадр                                | Успевает ли игра за реальным временем                          |
| Время приказа и задержка реакции                        | От получения команды до завершения расчёта и первого показанного результата | Подвисания при клике; это разные интервалы                     |
| CPU по потокам, время исполнения и ожидания             | Sampling/ETW-профиль                                                        | Вычислительное ограничение, блокировки или искусственная пауза |
| GPU execution/present/wait                              | Графическая системная трасса                                                | Загрузка GPU, ожидание синхронизации и очереди                 |
| Private bytes, working set, dedicated/shared GPU memory | По времени, включая пик загрузки и длительный матч                          | Требования RAM/графической памяти, рост кэшей и утечки         |
| Холодный/повторный запуск, первый показ ассета          | Отдельные интервалы загрузки                                                | Стоимость I/O, декодирования и создания ресурсов               |

Внутри рендера разделить CPU-подготовку, выдачу draw-команд и `EndDraw`. Длительность `EndDraw` не равна чистому времени GPU: там могут быть ожидания. Низкая суммарная загрузка CPU не исключает перегрузку главного потока, а низкая загрузка GPU может означать, что он ждёт CPU. На гибридном процессоре дополнительно фиксировать питание, частоты и размещение потока по ядрам.

Для CPU использовать Release с символами и [Visual Studio CPU Usage](https://learn.microsoft.com/en-us/visualstudio/profiling/cpu-usage?view=visualstudio), смотреть Self CPU и дерево вызовов по потокам без отладчика. Для корреляции системных событий — ETW и [Windows Performance Analyzer](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/windows-performance-analyzer). Подробные трассы собирать отдельно от итогового замера, чтобы оценить накладные расходы самого профилирования. Сборку с символами настроить отдельно, сохранив Release-оптимизации: текущий preset сам по себе не гарантирует достаточных символов всех модулей.

### Частота тиков, кадров и ожидание в цикле

В [Simulation.hpp](../include/rts/Simulation.hpp) задано **30 тиков в секунду**. Это 33,33 мс между обновлениями мира; частота рендера может быть другой. Для 60 FPS интервал кадра — 16,67 мс. В текущей последовательной архитектуре тик делит время главного потока с рендером, вводом и ожиданиями, поэтому «тик быстрее 33 мс» ещё не доказывает плавные 60 FPS.

В конце игрового и редакторского циклов стоит `MsgWaitForMultipleObjectsEx(..., 8, ...)`. Это ожидание до 8 мс, прерываемое вводом, а не точный ограничитель FPS. Вместе с синхронизацией представления кадра оно может влиять на плавность и отзывчивость. Измерить реальные интервалы; при подтверждённом влиянии перейти к ожиданию ближайшего срока кадра/тика и сообщений. Убирать ожидание без замены нельзя: это может поднять потребление CPU без улучшения изображения.

При долгой задержке `elapsed` ограничивается 0,25 с. Поэтому отдельно учитывать пропущенное реальное время при таком ограничении: небольшой accumulator после фриза не доказывает, что симуляция не замедлялась.

### Воспроизводимые сценарии

Подготовить карты и последовательности команд для: спокойной базы; движения 100 юнитов; боя 50×50; недостижимых целей и ворот; леса с масками; ночи с множеством источников; распределённого обзора; карты максимального поддерживаемого размера; длительного боя с останками и снарядами. Число объектов, типы юнитов, позиции камеры и время суток фиксировать. Replay/performance-сценарий для оконной игры пока только предлагается, существующий `--smoke-test` его не заменяет.

Практический протокол: Release, запуск локально вне отладчика; фиксированные разрешение/DPI/частота монитора и масштаб камеры; 30 секунд прогрева, затем 3 прогона по 3–5 минут на сценарий. Холодный старт измерять отдельно. Для памяти и нагрева — дополнительный матч 30–60 минут. Повторять на Windows 10 и 11, если обе платформы остаются заявленными. На ноутбуках не смешивать режимы от батареи и сети.

## Минимальные и рекомендуемые системные требования

**Сейчас подтверждены целевая платформа Windows 10/11 x64 и Release-работоспособность бенчмарка на Core Ultra 7 155H. Минимальный CPU, GPU, RAM и стабильные 30/60 FPS пока не установлены.** Даже для этой машины оконный FPS в данном аудите не измерялся. Нельзя честно присвоить игре требования уровня конкретной модели Core i3/Ryzen или видеокарты по одному замеру математического ядра.

Сначала принять критерии качества, затем выбрать самые слабые реальные конфигурации, которые их проходят. Ниже — **предлагаемые цели тестирования**, не уже достигнутые характеристики:

| Критерий            | Минимальный профиль                                                       | Рекомендуемый профиль                                                                |
|---------------------|---------------------------------------------------------------------------|--------------------------------------------------------------------------------------|
| Изображение         | 1280×720, обычный игровой рендер                                          | 1920×1080, обычный игровой рендер                                                    |
| Цель частоты        | 30 FPS                                                                    | 60 FPS                                                                               |
| Время кадра         | p95 ≤ 33,33 мс; p99 ≤ 50 мс                                               | p95 ≤ 16,67 мс; p99 ≤ 25 мс                                                          |
| Фризы во время игры | Отдельно учитывать каждый кадр >100 мс, исключая явно отмеченные загрузки | То же; для подтверждения не должно быть воспроизводимых фризов в обязательных сценах |
| Симуляция           | Стабильные 30 тиков/с без нарастающего долга                              | То же, с запасом главного потока под кадр                                            |
| Приказы             | Предлагаемый p95 расчёта ≤ 50 мс                                          | Предлагаемый p95 расчёта ≤ 20 мс                                                     |
| Память              | Нет систематического paging при полном составе сцены                      | Дополнительный запас на фоновые приложения и длительный матч                         |

Это цели со статистическими допусками, а не обещание строго непрерывных 30/60 FPS. Для более строгого качества надо ужесточить p99. Обязательный набор карт и допустимую сложность пользовательских карт нужно объявить: требования для демо-карты не гарантируют ту же скорость на максимально насыщенной карте 512×512. Отдельных пресетов Low/High этот документ не вводит.

Для первого раунда подобрать реальные тестовые ПК следующих классов:

- Слабая конфигурация для поиска нижней границы: CPU с 2 ядрами / 4 потоками, 8 ГБ RAM, встроенная графика, 720p.
- Кандидат на рекомендуемую: CPU с 4 ядрами / 8 потоками, 16 ГБ RAM, встроенная или начальная дискретная графика, 1080p.
- Текущий Core Ultra 7 155H как контрольный CPU и отдельная конфигурация с более быстрым GPU для проверки, ограничивает ли игру графика.

Это набор стендов для проверки гипотезы, **не системные требования и не рекомендация покупать такое железо**. Число ядер без модели, архитектуры и энерголимита не задаёт быстродействие; объём видеопамяти без GPU тоже. Ограничение affinity на быстром CPU не воспроизводит старый процессор, его кэш, память или встроенную графику.

RAM выбирать по пиковому потреблению всей системы и игры, а не по размеру исходных PNG. Сейчас сумма файлов `assets` около 52,5 МиБ, но декодированные изображения, копии для освещения, CPU/GPU-кэши и undo Forge существенно меняют потребление. Для места на диске измерять готовый Release-пакет с запасом на пользовательские карты и временные файлы. SSD можно оценивать по времени загрузки; его нельзя объявлять обязательным по имеющимся данным. Требования Forge публиковать отдельно, включая одновременную работу редактора и F9 play test.

Результат следующего полноценного прогона должен содержать таблицу «точная конфигурация → сцена/разрешение → frametime/тик/память → прошёл профиль или нет». Только после этого заполнять публичные строки CPU/GPU/RAM/место на диске. Сначала наиболее полезны телеметрия и воспроизводимый оконный сценарий; распараллеливание — последующее решение по найденному ограничению.
